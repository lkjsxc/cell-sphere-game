## 1. Executive outcome

At completion, the sphere should feel physically responsive rather than merely draggable.

1. A deliberate fast flick on Home or World turns the sphere immediately under the pointer and then carries it through approximately one additional full turn after release.
2. The release remains bounded. It visibly loses energy, converges to stillness, and cannot spin forever.
3. A medium flick carries proportionally less distance. A slow inspection drag stops on release and remains suitable for selecting and examining individual cells.
4. Mouse and touch gestures with equivalent recent angular input produce the same class of result. Pen remains covered through the existing Pointer Events path when evidence is available.
5. A new pointer interaction, wheel input, meaningful keyboard activity, focus entry, a transient surface, programmatic focus framing, scene change, World replacement, hidden-page transition, or reduced-motion change stops or suppresses carried motion according to the existing trusted-interaction contract.
6. Direct manipulation remains immediate. No smoothing is inserted between the pointer and the sphere while the pointer is down.
7. Tap, drag, pinch, wheel, and cancellation remain distinct. A drag, pinch, cancellation, or residual release must not select or purchase a cell.
8. Home and World still begin from stillness and enter the existing calm automatic orbit only after the existing idle delay. The idle orbit is not made faster to satisfy this campaign.
9. Reduced motion retains direct drag and zoom but disables nonessential release inertia and automatic orbit.
10. The free-orbit frame remains orthonormal through repeated pole traversal and long-running motion.
11. Camera motion remains presentation-only. It cannot change ticks, RNG, Environment, Evolution, SCORE, Echoes, History meaning, World identity, settlement, Worker/fallback results, renderer semantics, or persistence.
12. No player-facing camera tuning control is added.
13. The production browser harness measures cumulative angular travel throughout a release. It does not mistake a final orientation that wraps around the sphere for little or no motion.
14. Current documentation no longer presents the existing conservative release calibration as the intended final feel.

## 2. Why this campaign was selected now

The latest user direction contains several valid concerns, but they do not form one dependency-closed implementation boundary.

The immediately preceding campaigns already completed and released:

- the six-step ordinary speed ladder and `1×` normal pacing contract;
- the 13.5-second Result continuation;
- wide two-thirds sphere composition;
- direct drag, bounded release inertia, and calm Home/World idle orbit;
- one shared living-boundary semantic for WebGL2 and Canvas 2D;
- CI, Pages, and deployed renderer evidence for the current `main` revision.

Those systems must not be reimplemented merely because an older prompt still names them.

The new complaint about release feel is nevertheless a direct contradiction of the current player experience. The current implementation proves that release inertia exists and is bounded, but it does not prove that a deliberate flick carries enough angular distance to feel like “spinning the sphere.”

At the orientation revision, the current camera defaults are:

- maximum release angular speed `2.4 rad/s`;
- damping half-life `360 ms`;
- hard inertia lifetime `2,500 ms`;
- minimum release speed `0.08 rad/s`;
- idle delay `4,500 ms`;
- idle orbit speed `0.022 rad/s`.

For the existing exponential integration model, the ideal maximum post-release path before the hard lifetime is approximately:

```text
1.236 radians
≈ 70.84 degrees
≈ 0.197 turns
```

That is bounded and technically correct, but it is not a vigorous spin. The existing browser oracle checks that motion continues briefly after release and remains below the speed clamp; it does not measure total release travel. A previous exact-content fallback run also observed a synthetic touch release near `2.204 rad/s`, so merely raising the maximum clamp would not reliably make that touch gesture energetic.

This campaign therefore corrects the release-response product boundary, not the direct-drag scale, simulation, idle orbit, or general camera architecture.

### 5.2 Selected design

Keep the existing direct-drag, sampling, state-machine, and exponential-integration architecture.

Add one pure progressive release-response mapping inside `camera-motion.js` or the current equivalent owner.

The selected mapping is:

```text
rawSpeed = magnitude of the recent angular-velocity estimate

if rawSpeed <= releaseThreshold:
    no inertia
else:
    u = clamp((rawSpeed - releaseThreshold)
              / (fullFlingInputSpeed - releaseThreshold), 0, 1)
    outputSpeed = maximumAngularSpeed * u²
    preserve the raw velocity direction
    if outputSpeed <= stopSpeed:
        no inertia
```

Use this initial selected constant set unless active-checkout measurement proves that the raw input units or current owner have materially changed:

```text
sampleCapacity          = 6       // unchanged
sampleWindowMs          = 120     // unchanged
releaseThreshold        = 0.30 rad/s
fullFlingInputSpeed     = 2.20 rad/s
maximumAngularSpeed     = 8.00 rad/s
dampingHalfLifeMs       = 600 ms
stopSpeed               = 0.025 rad/s
maximumInertiaMs        = 5,000 ms
idleDelayMs             = 4,500 ms // unchanged
idleOrbitSpeed          = 0.022 rad/s // unchanged
maximumFrameMs          = 100 ms // unchanged
```

Under the continuous exponential model, the selected maximum output integrates to approximately:

```text
6.903 radians
≈ 395.54 degrees
≈ 1.099 turns
```

That calculation is design orientation, not the final browser oracle. Final acceptance uses cumulative measured camera-basis travel through the production controller.

The progressive response is selected instead of a uniform gain because it:

- leaves slow precision gestures still;
- gives medium gestures proportionate carry;
- promotes a deliberate high-speed mouse or touch flick into the energetic class;
- does not alter direct drag sensitivity;
- avoids relying on the existing maximum clamp when a strong touch trace may remain below it;
- remains pure, deterministic, bounded, and easy to test.

Preserve the existing exponential elapsed-time integration. Do not replace it with frame-count damping, a spring, a physics dependency, or a generic gesture framework.

## 7. Detailed target state

### 7.1 Direct manipulation remains unchanged

Preserve the existing direct pointer-to-angular-delta scale unless active inspection proves it has already changed under newer explicit policy.

A pointer move must still rotate the sphere immediately in the same event path.

Do not insert:

- lag filtering;
- easing;
- velocity prediction;
- animation-frame batching that delays direct drag;
- device-specific sensitivity constants;
- a touch-only or mouse-only camera path.

The release response begins only after a valid drag ends.

### 7.2 Gesture classification remains unchanged

Preserve the current cumulative-travel and elapsed-time distinction among:

- tap;
- drag;
- pinch;
- pointer cancellation.

Required consequences:

- tap may select;
- drag never selects on release;
- pinch never becomes a tap;
- cancellation never creates inertia;
- non-primary mouse buttons do not start a normal drag;
- wheel zoom cancels release motion and does not manufacture angular velocity;
- a second pointer terminates one-pointer release sampling safely.

Do not loosen tap thresholds merely to create more flicks.

### 7.3 Release estimation remains bounded

Keep the fixed-capacity recent sample buffer and time window.

Velocity must be based on recent angular movement, not total gesture distance from pointer-down.

A long hold followed by one small move must not be treated as a fast flick.

Queued handler delivery must use the event timestamp for velocity estimation. The idle deadline must remain anchored to observed animation time.

Reject nonfinite values and incompatible clock domains safely.

### 7.4 Progressive release response

The response mapping is the only new product behavior.

It must:

- preserve velocity direction;
- be monotone in raw speed;
- be zero at and below the release threshold;
- remain finite;
- saturate at the selected maximum;
- have bounded constant-time work;
- contain no per-device branch;
- contain no random input;
- contain no frame-rate input;
- create no persistent state;
- be independently testable.

The selected quadratic response is intentionally conservative below the high-speed knee and energetic above it.

Do not add a generic easing catalog or user-selectable curve.

### 7.5 Exponential damping and path bounds

Continue using elapsed animation time and the analytic exponential integral per step.

For a velocity magnitude `v`, half-life `h`, and elapsed step `dt`, the implementation should preserve the existing frame-rate-independent form or a mathematically equivalent form.

Do not:

- multiply velocity by a fixed per-frame factor;
- skip an animation delta without a defined hold/reset reason;
- integrate hidden-page catch-up;
- retain velocity after the hard lifetime;
- let a nonfinite delta mutate the camera;
- use game speed to change damping.

The hard lifetime remains a safety bound, not the primary ordinary stopping mechanism. The selected half-life and stop threshold should make a maximum release approach stillness naturally by the hard bound.

### 7.6 Cumulative angular-travel oracle

Final orientation alone is not a valid release-distance oracle because approximately one full turn can end near the starting direction.

For pure tests and structured browser evidence, sample the camera frame throughout release and accumulate incremental angular travel.

A valid direction-based measure may sum:

```text
acos(clamp(dot(direction[n - 1], direction[n]), -1, 1))
```

A complete basis measure may additionally verify `up` and `right` to catch roll or orthonormality defects.

Requirements:

- sampling is bounded;
- test evidence may record a bounded trace or aggregate only;
- production does not retain an unbounded camera history;
- the metric is observational and cannot feed back into motion;
- browser evidence reports raw release speed, mapped speed, cumulative post-release travel, duration, cancellation state, and final basis validity;
- screenshots remain supplemental.

### 7.7 Canonical trace classes

Codex may encode these through the existing public controller API rather than exact event-object mocks, but their angular meaning must remain explicit.

#### Strong trace

A representative current-browser-like trace:

- six total samples including the origin;
- five movement samples over approximately `80 ms`;
- cumulative angular delta approximately `(0.66, 0.26)` radians;
- valid drag release.

Expected post-release travel:

```text
0.90–1.25 turns
```

#### Medium trace

A deliberate but non-maximal trace:

- recent movement over approximately `100–120 ms`;
- cumulative angular delta selected to produce a raw speed near `1.1–1.5 rad/s` in the active implementation;
- valid drag release.

Expected post-release travel:

```text
0.18–0.50 turns
```

#### Slow precision trace

A sustained slow inspection drag:

- movement distributed over at least `220 ms`;
- recent raw speed below the release threshold;
- valid drag classification due to cumulative travel.

Expected post-release behavior:

```text
no inertia
zero cumulative post-release travel
```

The exact pixel fixture may vary by viewport. The angular trace is the stable oracle.

### 7.8 Idle orbit remains calm

Keep idle automatic motion separate from release response.

Preserve:

- Home and World only;
- new scene/World starts still;
- `4,500 ms` fresh idle delay;
- `0.022 rad/s` orbit speed;
- immediate cancellation by trusted activity;
- surface holds;
- hidden-page suspension without catch-up;
- reduced-motion suppression;
- no Evolution or Trophy auto-orbit.

Do not make idle orbit use the release-response curve.

### 7.9 Trusted cancellation and lifecycle

After any of the following, carried release velocity must be zero before another automatic movement step:

- trusted pointer-down;
- wheel;
- meaningful trusted keyboard input;
- trusted focus entry outside the programmatic-focus guard;
- opening or closing a coordinated surface according to current policy;
- programmatic focus framing;
- scene change;
- World replacement;
- hidden-page transition;
- reduced-motion activation;
- pointer cancellation;
- pinch transition.

Closing a hold or returning visible begins a fresh idle wait. It does not resume old release velocity.

### 7.10 Accessibility

Under reduced motion:

- direct drag and zoom remain available;
- no release inertia occurs;
- no automatic orbit occurs;
- no hidden residual velocity accumulates;
- camera focus does not animate unless an existing essential accessible behavior requires it;
- focus and keyboard operation remain unchanged.

Forced colors and high contrast should not be affected because this campaign changes motion only, but the existing browser paths must remain passing.

Do not add a motion announcement or live-region chatter for every release.

## 10. Acceptance criteria

Every criterion below is independently decidable.

### 10.1 Progressive response mapping

- Raw speed at or below the final threshold yields no inertia.
- The mapped magnitude is monotone over the accepted finite raw range.
- The mapped magnitude never exceeds the final maximum.
- The mapped vector preserves raw direction within floating-point tolerance.
- Nonfinite raw input cannot create motion.
- A mapped magnitude at or below stop speed yields no inertia state.
- Work is constant-time and allocation-free in the hot path.
- One owner contains the mapping and constants.

### 10.2 Strong release

For the canonical strong angular trace:

- release enters inertia;
- cumulative post-release travel is at least `0.90` turns;
- cumulative post-release travel is at most `1.25` turns;
- motion ends by `5,100 ms` under ordinary cadence;
- final speed is zero after completion;
- every camera vector is finite;
- the final basis is orthonormal within the repository's established tolerance;
- a new direct interaction stops the release immediately.

### 10.3 Medium release

For the canonical medium trace:

- release enters inertia;
- cumulative post-release travel is at least `0.18` turns;
- cumulative post-release travel is at most `0.50` turns;
- travel is less than the strong trace by a clear margin;
- motion converges without a hard visible rebound;
- cancellation remains immediate.

### 10.4 Slow precision drag

For the canonical slow trace:

- the gesture remains classified as a drag rather than a tap;
- direct manipulation occurs;
- release does not enter inertia;
- cumulative post-release travel is zero within numerical tolerance;
- no delayed automatic orbit begins before a fresh idle deadline;
- cell selection is not triggered by release.

### 10.5 Absolute safety bounds

For extreme finite input and malformed inputs:

- mapped release speed never exceeds the final maximum;
- cumulative post-release travel never exceeds `1.35` turns;
- inertia lifetime never exceeds `5,100 ms` plus one test-frame tolerance;
- sample count never exceeds capacity;
- no `NaN` or infinity enters camera state;
- no unbounded array, timer, listener, or trace is created;
- pointer cancellation and scene replacement leave zero velocity.

### 10.6 Frame-cadence independence

Run the same strong and medium traces at 30, 60, 120, and 144 Hz.

Require:

- cumulative path spread no greater than `2.5%` relative to the 60 Hz reference;
- release-duration spread no greater than one frame at the slower cadence plus `25 ms`;
- final camera direction, right, and up vectors within `1 degree` of the 60 Hz reference after completion;
- no frame-count damping;
- no skipped animation-time integration other than established holds.

### 10.7 Delayed input delivery

For equivalent input timestamps observed with `0`, `150`, and `350 ms` handler delay:

- raw release-speed class remains within `5%`;
- cumulative post-release path remains within `5%`;
- idle deadline remains based on observed animation time;
- no stale sample is accepted outside the configured input-time window;
- incompatible epoch timestamps use the safe current fallback.

### 10.8 Mouse, touch, and pen semantics

In the trusted production browser:

- strong mouse and strong touch gestures each reach the strong release class;
- their cumulative post-release travel differs by no more than `15%` when their angular trace and duration are equivalent;
- both remain inside the absolute path and lifetime bounds;
- touch does not create a synthetic tap after release;
- pinch and pointer cancellation produce zero release velocity;
- pen is verified when real or supported trusted evidence is available and otherwise classified unavailable, not passed.

### 10.9 Trusted cancellation

Each relevant cancellation source must be tested independently.

After cancellation:

- motion mode is no longer inertia or orbit as appropriate;
- release speed is zero;
- camera direction remains unchanged over a subsequent bounded observation window unless direct manipulation occurs;
- a fresh idle deadline exists where appropriate;
- old velocity cannot resume.
